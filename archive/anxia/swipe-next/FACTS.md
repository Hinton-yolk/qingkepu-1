# FACTS · 「你按下去之后」· 你上划之前

只讲公开、通用的原理；不涉及任何平台未公开的参数或权重。

| 片中说法 | 依据 | 来源 |
|---|---|---|
| 「你的手指还没往上划，下一条其实已经在你手机里了」「在你看这一条的时候，它就被悄悄下载好了，后面往往还排着两三条」 | 短视频 App 普遍做「预加载」：当前视频播放时，提前下载后面几条的开头部分，划过去就能秒开。字节跳动旗下 BytePlus 的播放器最佳实践建议：当前视频缓冲超过约 20 秒（或缓冲完）后开始预加载，**建议预加载 3 个视频**，每个约 800 kB；用户一划就取消没用上的预加载。阿里云的方案说明了预加载 + 封面能把起播时间压到几百毫秒。**「两三条」是常见配置，不同 App、不同网络会不一样，所以用了「往往」** | BytePlus VOD「Android player short video best practices」「Custom preloading」；阿里云视频点播文档；学术论文 PDAS、DeLoad（arXiv 2510.18459）等短视频预加载研究 |
| 「你在这条视频上停留的每一秒，都会变成一个信号，飞回机房」 | 推荐系统把你的行为（看了多久、看没看完、点赞、评论、分享、划走）作为反馈。抖音官方说明：点赞优于不点赞、**看完优于没看完**，点「不感兴趣」是负面反馈。「每一秒」是**概括说法**，指停留时长被记录为信号 | 抖音「安全与信任中心」网站（2025-03-30 上线，首次公开推荐算法原理）；新浪科技、财联社、北京日报报道 |
| 「系统先从海量视频里，捞出一小批你可能喜欢的」 | 推荐系统通常分「召回 → 过滤 → 排序」几步：先从海量内容里召回一小批候选，再细排。YouTube 2016 年公开的论文同样是「候选生成 + 排序」两段式，从数百万视频里先缩到几百条 | 抖音安全与信任中心（召回、过滤、排序）；Covington, Adams, Sargin (2016), *Deep Neural Networks for YouTube Recommendations*, RecSys |
| 「再给每一条算一道题：你会看完吗？会点赞吗？会评论、会分享吗？」 | 抖音官方：推荐系统几乎不依赖打标签，而是用神经网络**直接预估每个用户对每条内容的点赞、关注、分享、评论等行为的概率**，再结合各行为的价值权重给候选打分；YouTube 论文的排序目标是预估观看时长 | 抖音总裁韩尚佑在 2025 中国网络媒体论坛的介绍；安全与信任中心；YouTube 论文 |
| 「分数最高的几条，赶在你划之前，送回你的手机排好队」 | 排序后得分最高的内容下发到 App，再由预加载提前下好（**简化说法**：实际是一次请求下发一批，App 再按顺序预加载） | 同上 |
| 「你每刷一会儿，这一整套就重新跑一遍」 | App 每刷完一批就会请求下一批推荐，系统按最新的反馈重新召回、排序（**概括说法**） | 同上 |
| 「你以为是你在刷视频。其实，视频也在刷你」 | **比喻**：你的每次停留都被当作反馈，影响下一批推荐 | — |
| 「不想看的，别盯着看；长按『不感兴趣』，才是你能直接说『不』的方式」 | 「看完优于没看完」意味着停留本身是正面信号；「不感兴趣」是官方明确列出的负面反馈。**不说**「评论骂它会让它更火」之类没有公开依据的说法 | 抖音安全与信任中心 |

## 画面里的示意（不是实测）

| 画面 | 说明 |
|---|---|
| 前三名的号码贴纸、只有三张卡被送回 | **简化**：实际一次下发一批（数量各 App 不同），画面只画前三张，和片头「后面往往还排着两三条」对应 |
| 「第 N 轮」计数越来越快 | **示意**：表示「刷一会儿就重新跑一遍」，数字不是任何平台的真实请求次数 |
| 机房里滚动的「你」的卡片（停留 12 秒、看完了、划走 · 1 秒、点了赞……） | **示意**：表示你的行为被当作反馈记录下来；具体记哪些、怎么存，片中不涉及 |
| 盯着灰色视频看，排队里和机房窗口里出现更多灰色的同类视频 | **示意**：把「看完优于没看完」（停留是正面反馈）画成「同类变多」。平台没有公开「看几秒就多推几条」这类数字，片中不给数字 |
| 长按出现的纸菜单（不感兴趣 / 倍速播放 / 清屏播放） | 通用画法，不照搬任何 App 的界面；「不感兴趣」是官方列出的负面反馈 |
| 点「不感兴趣」后，灰色同类从队列里掉出、窗口翻黑 | **示意**：负面反馈会降低这类内容的推荐，画面把它画成「立刻被换掉」；实际效果的快慢和幅度平台没有公开 |
| 片尾屏幕里换成日出 | 纯画面：表示「下一条」已经换了，不代表任何具体内容 |
